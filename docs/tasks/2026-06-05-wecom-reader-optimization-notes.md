# 企微读取链路优化记录

## 背景

本次运行中，企业微信 Agent 的左侧会话列表正常抓取耗时约 `4-6s/轮`，同时后半段出现多次 `single_chat_row_not_found`。从现象看，定位失败并不一定代表企微窗口真的不可用，更可能是每轮都重新定位“单聊”时受到 AX 树刷新、焦点变化、侧边栏/弹窗、窗口状态等影响。

## 优化点：缓存单聊定位，异常时再恢复

当前链路每轮扫描都倾向于先确认/定位“单聊”。如果鼠标位置、窗口位置、企微窗口焦点和页面结构都不变，理论上“单聊”分组位置应该稳定，不需要每轮重新搜索和点击。

建议改为：

- 启动时确认并缓存“单聊”分组位置与当前会话列表区域。
- 正常扫描时优先直接读取缓存的会话列表区域，不每轮点击“单聊”。
- 只有在读取结果异常时再触发恢复逻辑，例如：
  - 连续多轮读取 `row_count=0`。
  - 会话列表区域坐标明显失效。
  - 检测到窗口切换、窗口尺寸变化、AX 树结构变化。
  - 明确出现 `single_chat_row_not_found` 且连续达到阈值。
- 对单次 `single_chat_row_not_found` 先记日志，不立即判定链路失效。
- 恢复逻辑再执行 `ensure-single-chat`，必要时重新全屏/重新定位。

## 预期收益

- 减少每轮 AX 搜索和点击动作。
- 降低“单聊”节点短暂消失造成的误判。
- 提升稳定性，避免因为一次定位失败导致后续空扫。
- 为后续读取耗时优化提供更干净的基线。

## 待讨论

- 缓存失效阈值：连续失败几次后恢复比较合适。
- 是否记录窗口 frame / sidebar frame / conversation table frame 作为缓存签名。
- 当前聊天窗口打开后是否可能改变左侧列表区域，需要用日志确认。
- 是否允许用户配置“固定单聊模式”，在测试期完全跳过每轮 ensure。
